## 1. ملخص تنفيذي

**ما المنصة:** منصة ويب عربية (RTL) تدير برنامج **صقل** لتنمية وتأهيل القيادات الشبابية من طلاب الجامعات (18–22 سنة) في المدينة المنورة، لبرنامج واحد وعدد مستخدمين صغير (~28 مشاركاً + ~8 فريق عمل + زوار الداعم).

**لمن:** تجربتان: (1) المشارك: يتعلم بالممارسة؛ يحضر ويقدّم في لقاءات التركيز ويبني خطته الشخصية، وفي رحلات مجموعته يكون **معدّاً ومنفّذاً**. (2) فريق العمل والإدارة: قائد عام، ميسّرون لأربع مجموعات، لجان مالية وإعلامية وتقنية، ومتابع رحلات. وجهة ثالثة: **الداعمون والشركاء** برابط خاص، وزوار **الموقع التعريفي**.

**المشكلة:** البرنامج كثير الدورات المتشابكة: رحلات تمر بـ3 نماذج واعتماد ثلاثي، مالية صارمة (مرصود، عهد، فواتير، إغلاق)، تقييم 50/50 بنقاط كسب فقط تُحسب من نشاط المنصة، ومواعيد نهائية. المنصة تجعل كل واحد يعرف **«ما المطلوب منه الآن»**، وتجعل القواعد (الصلاحيات، المال، النقاط) مفروضة بالنظام لا بالمتابعة اليدوية، وتترك أثراً لا يُمحى لكل قرار مالي.

**المبادئ المعمارية (من القرارات):**
1. كل ما يمكن ضبطه **في قاعدة البيانات** لا الكود (أوزان، مستهدفات، تصنيفات، قوائم) وتعديله لا يكسر شاشة.
2. الصلاحيات تُفحص **في الخادم** (وفي قاعدة البيانات للحساس) لا بإخفاء الواجهة؛ والممنوع كغير الموجود.
3. السجلات المعتمدة لا تُعدَّل مباشرة: طلب تعديل بموافقة القائد العام، وسجل تدقيق لا يُحذف.
4. كل مبلغ له مرفق إثبات.
5. النقاط كسب فقط ومحسوبة تلقائياً قدر الإمكان.
6. بساطة للمستخدم: زر رئيسي واحد، حالة بنص وخطوة تالية، جوال أولاً.

**النتيجة المطلوبة:** تطبيق ويب واحد (Next.js + PostgreSQL) بخادم صغير ومجدول مهام داخلي، يعيد إنتاج سلوك الديمو بالضبط (نتائج النقاط والمسارات والأرقام) مع المصادقة والتخزين والتدقيق الحقيقيين.

## 2. الأدوار والصلاحيات

### 2.1 مبدأ الصفات المتعددة
الشخص له **نوع أساسي** (`participant` | `staff`) ويحمل **صفات** تُشتق من البيانات (لا تُخزَّن): ميسّر مجموعة، قائد مجموعة، مسؤول/عضو لجنة (مالية، إعلامية، تقنية، عامة)، متابع رحلات (دائم أو بديل لرحلة)، عضو/قائد فريق رحلة لفريق العمل، مقدّم في لقاء، مسؤول تحضير، ومفوَّض مؤقت. **الصلاحيات الفعلية = اتحاد صلاحيات كل صفاته** ثم يُطبَّق عليها **الفيتو**.

```
can(actor, action, resource):
    caps = capabilities(actor)                     -- مشتقة بـ ~6 استعلامات لكل طلب (تُخزَّن بالطلب)
    allowed = ∃ c ∈ caps : rule(c, action, resource)       -- اتحاد
    veto    = selfApproval(actor, resource)                -- صاحب الطلب لا يعتمد طلبه
           ∨ reviewerIsHolder(actor, resource)             -- المراجع لا يراجع عهدته
           ∨ stateForbids(resource.state, action)          -- الحالة (آلات القسم 5)
           ∨ timeLocked(resource)                          -- بند بدأ، موعد، قفل التقييم
           ∨ capacityConflict(actor, action)               -- قواعد التعارض
           ∨ preFormation(actor, resource)                 -- المشارك قبل نشر التشكيل
    return allowed ∧ ¬veto        -- الرفض موحّد access_denied (لا تسريب وجود)
```
مثال: «يوسف» مشارك (يرى الرحلات العامة) + قائد مجموعة أُحُد (يرفع نماذج رحلة أُحُد ويستلم عهدتها ويسجل حضور لقاءات تركيزها) + مقدّم في لقاء (يرى لقاءه) + عضو لجنة إعلامية (يرى مساحتها). لا يرى خطط مجموعة قُباء، ولا يعتمد طلبه المالي ولو فُوِّض.

### 2.3 الفيتوهات والتعارضات (ملخص)
- **صاحب الطلب لا يعتمد طلبه** (BR-015) · **المراجع لا يراجع عهدته** (BR-016).
- **المتابع** ليس ميسّر الرحلة، وفي رحلات الفريق ليس ق.ع (BR-217).
- **قواعد التعارض** (BR-009/010): مسؤول المالية بلا صفة ثانية؛ مسؤولو اللجان ليسوا ميسّرين؛ المتابع الدائم ليس ميسّراً ولا مسؤول لجنة؛ م.ت ليس المتابع الدائم.
- **قبل نشر التشكيل** يُسقَط عن المشارك كل ما يرتبط بالمجموعات (BR-017).
- **اللجان**: عضو اللجنة يرى لجنته فقط، وق.ع يرى الكل.
- تفاصيل الصلاحيات المالية الست في [07-finance.md §7.1](07-finance.md).

## 3. النطاقات (Modules)

> لكل وحدة مجلد `server/modules/<name>` (خدمة + مستودع + مخططات) و`features/<name>` (واجهة). الوحدات لا تستدعي بعضها إلا عبر **الواجهات العامة** المذكورة (`depends`)، ولا تقرأ جداول بعضها مباشرة إلا عبر views للقراءة.

### 12.3 الطبقات وتدفق الطلب

```
المتصفح (React, RTL)
   │  TanStack Query ── HTTPS ──►  Route Handler  /api/v1/...
   │                                  │ 1) CSRF/Origin + جلسة → actor
   │                                  │ 2) Zod validate (contracts)
   │                                  ▼
   │                           Service (server/modules/x)
   │                                  │ 3) BEGIN; SET LOCAL app.user_id = actor
   │                                  │ 4) can(actor, action, resource)  ← packages/domain
   │                                  │ 5) تحميل الكيانات FOR UPDATE + تحقق الحالة (آلات القسم 5)
   │                                  │ 6) الكتابة + audit_log + outbox(events)
   │                                  │ 7) COMMIT
   │                                  ▼
   │                         PostgreSQL (قيود + triggers + RLS)
   │                                  ▲
   └─────────────────────  pg-boss Worker: يعالج outbox (إشعارات، points_run) + المجدولات
```
**قواعد البنية:** المنطق في `packages/domain` (نقي) و`server/modules/*/service.ts`؛ **لا منطق في Route Handlers ولا في مكوّنات React**؛ الخدمات هي الوحيدة التي تفتح معاملات؛ كل كتابة تمر بـ`audit` عند الحاجة.

### 12.4 تطبيق الصلاحيات
1. **التطبيق (الأساسي):** `can()` من `packages/domain` مع `Capabilities` تُحمَّل من SQL، وتغطي الفيتوهات.
2. **قاعدة البيانات (دفاع ثانٍ):** RLS مفعّلة على: `facilitator_note, personal_plan(+فروعها), life_aspect, plan_step, step_follow_up, bank_account, account, audit_log` وكل جداول المالية. الاتصال يضبط `SET LOCAL app.user_id` و`app.roles`؛ السياسات تُنسخ القواعد الجوهرية (مثلاً: خطة شخصية يقرؤها صاحبها أو ميسّره أو ق.ع؛ مرفق مالي لصاحب العهدة أو مالية). دور DB للتطبيق **بلا** `BYPASSRLS` ولا `UPDATE/DELETE` على الجداول append-only.
3. **اختبار مزدوج:** كل قاعدة وصول لها اختبار على طبقة الخدمة وآخر مباشر على SQL (يتأكد أن إغفال فحص التطبيق لا يُسرّب البيانات).
4. **الواجهة** تخفي ما لا يملكه المستخدم (راحة) وتقرأ `GET /auth/me` للقوائم.

### 12.5 العربية RTL والجوال
- `<html lang="ar" dir="rtl">`؛ **خصائص CSS المنطقية** فقط (`ms-/me-/ps-/pe-/start/end`, `inset-inline`, `text-start`)، أيقونات الاتجاه تُعكس (`rtl:rotate-180`).
- أرقام لاتينية (كما قرر الديمو)، `font-variant-numeric: tabular-nums` في الجداول المالية، الهجري بجانب الميلادي (إعداد).
- الخط: IBM Plex Sans Arabic (أو ثمانية سانس — س-10) مستضاف ذاتياً بـ`font-display: swap`؛ مقياس: نص 16، صغير 14، لا أصغر.
- جوال أولاً: شريط سفلي (الرئيسية، التقويم، أهم عنصرين للدور، «القائمة»)، الجداول الكثيفة (مراجعة الفواتير) تتحول لبطاقات، أهداف لمس ≥44px، نماذج بخطوات وشريط تقدم، `inputmode` للأرقام والآيبان، تحقق من `viewport`.
- التواريخ/الأوقات تُنسَّق بـ`Intl` `ar-SA-u-ca-gregory-nu-latn`.
- اختبار بصري/وظيفي: Playwright بإطارين (390×844 و1440×900) وفي RTL.
- PWA خفيفة (manifest + أيقونة) لتثبيت المنصة على الجوال؛ الإشعارات الدافعة خارج النطاق الحالي.

### 12.6 البريد (مؤجل) والاستضافة
- واجهة `Mailer` بتنفيذ `NoopMailer` الآن؛ لاحقاً Resend/SES، وقوالب RTL، وتفعيل «المهم» من `notification_policy`.
- الاستضافة: **قرار مفتوح** (س-01). المتطلبات: Postgres مُدار بنسخ احتياطي PITR، تخزين كائنات، عملية Node واحدة (+عامل)، TLS، متغيرات أسرار. يصلح VPS صغير، أو PaaS (Render/Fly/Railway)، أو سحابة.

### 12.7 السعة وعدم الإفراط في التعقيد
~40 مستخدماً داخلياً، ذروة صغيرة (نشر التشكيل، يوم رحلة، زوار الداعم). كافٍ: خادم 1–2 vCPU، قاعدة صغيرة، **بلا Redis، بلا Kubernetes، بلا microservices، بلا WebSocket** (استطلاع 30–60ث للجدول الحي). النقاط تُحسب بالدفعات، وتخزّن مؤقتاً (`points_entry`). أي تعقيد إضافي يُبرَّر بحادثة فعلية.

## 14. الأمان والخصوصية

| المجال | الإجراء |
|---|---|
| **عزل البيانات حسب الدور** | `can()` على كل نقطة + RLS على الحساس + `access_denied` موحَّد (BR-014) + اختبارات تسرّب (مورد موجود/غير موجود يتماثلان) |
| **الآيبان والباركود** | جدول مستقل؛ الآيبان مشفّر على مستوى التطبيق (AES-256-GCM، مفتاح من إدارة الأسرار/KMS مع تدوير)؛ قراءة محدودة وبسجل اطلاع؛ لا يُسجَّل في logs |
| **الفواتير والمرفقات المالية** | بكت خاص + روابط موقّعة 5 دقائق + صلاحية الكيان الحامل + تدقيق التنزيل؛ لا حذف |
| **الخطط الشخصية وملاحظات الميسّر** | RLS: صاحبها/ميسّره/ق.ع فقط؛ ملاحظات الميسّر: فريق العمل فقط؛ استبعادها من أي تصدير عام |
| **سجل التدقيق** | append-only (REVOKE + trigger)، سلسلة تجزئة اختيارية، يُسجَّل: الحسابات، الأدوار، المال، الإعدادات، اطلاع الآيبان، الدخول الفاشل/الناجح [جديد `security`] |
| **جلسات الدخول** | Argon2id (m=19MiB,t=2,p=1 أو أعلى)؛ كوكي `HttpOnly; Secure; SameSite=Lax`؛ جلسة منزلقة 12 ساعة وحد 7 أيام؛ تدوير المعرّف عند الدخول؛ إبطال الكل عند تغيير الكلمة؛ حد محاولات 5/15 دقيقة؛ كلمة مؤقتة تُجبر على التغيير؛ عرض الكلمة المؤقتة مرة واحدة |
| **CSRF/XSS** | فحص Origin + رمز؛ CSP صارم (`default-src 'self'`، بلا inline)؛ تنقية HTML (لا HTML من المستخدم أصلاً: نص فقط؛ SVG الشعارات بعد تنقية)؛ رؤوس أمان (HSTS، X-Content-Type-Options، Referrer-Policy) |
| **حقن SQL** | معاملات مرتبطة دائماً (Drizzle) |
| **حماية رابط الداعم** | 11.2: كلمة لكل جهة بـHMAC فريد + Argon2id، حد 5/15 دقيقة لكل IP، noindex، جلسة منفصلة 8 ساعات، لا بيانات مالية/نقاط/شخصية، تأخير ثابت للاستجابة، تعليقات بمراجعة |
| **الملفات** | قائمة MIME مسموحة، حد الحجم، إعادة تسمية، sha256 خادمي، فحص خبيث اختياري، لا تنفيذ |
| **الأسرار والبيئة** | متغيرات بيئة/مدير أسرار؛ لا مفاتيح في المستودع؛ seed dev محروسة (`production` ⇒ رفض) |
| **النسخ الاحتياطي** | PITR يومي للقاعدة (احتفاظ ≥ 30 يوماً) + versioning للبكت + اختبار استعادة ربع سنوي |
| **المراقبة** | تنبيه على فشل المهام، ارتفاع 403/401، فروق `reconcile` المالية |
| **نظام حماية البيانات الشخصية والاستضافة** | **نقطة تحتاج قراراً** (س-01): الأساس النظامي لمعالجة بيانات الأفراد والمالية، موقع الاستضافة ونقل البيانات خارج المملكة، مدة الاحتفاظ والحذف، الموافقة الصريحة على نشر صور وأرقام فريق العمل، سجل المعالجة، حقوق الوصول والتصحيح. أُوصي بمراجعة نظامية قبل الإطلاق |
| **الأسماء الحقيقية في بيانات الديمو** | لا تُنقل لأي بيئة؛ seed مُخفى الهوية (15.3، س-16) |

- **أين يوضع منطق الأعمال بعيداً عن الواجهة؟** في `packages/domain` (قواعد نقية قابلة للاختبار بلا DB) و`server/modules/*/service.ts` (تنسيق المعاملات). ملف `eslint` يمنع استيراد `react` أو `next` أو `drizzle` داخل `packages/domain`، ويمنع `features/` من استيراد `server/`.
- **تسمية الوحدات:** مفرد إنجليزي بأسماء القسم 3 (`identity, groups, trips, focus, individual, evaluation, finance, committees, meetings, library, surveys, notifications, calendar, site, files, audit, settings`). ملفات الجداول `snake_case`، المكوّنات `PascalCase`، الدوال `camelCase`.

### سيناريوهات القبول (نماذج؛ تُشتق بقيتها من اختبارات الديمو)
1. **أول دخول للمالية:** م.م بلا موازنة ← يظهر المعالج؛ لا طلبات تُقبل؛ بعد الحفظ تُقفل (BR-505).
2. **عضو مالي بلا صلاحيات:** أنس يدخل «المالية» فيرى الطلبات فقط، ولا أزرار صرف؛ API يعطي 403 (BR-501).
3. **لقاء التركيز رقم 9:** الميسّر ينشئ؛ لا طلب ميزانية ويظهر السبب (BR-303).
4. **طلب فوق المرصود:** 1860 على عمرة مرصودها 1500 ← `pending_leader` ← ق.ع يعتمد ← م.م يحوّل (BR-509).
5. **نشر الرحلة:** ناقص ضيف غير مؤكد ← زر معطّل والـAPI `rule_violation` بالشرط (BR-210).
6. **رفض ق.ع للجدول:** يعود لقائد المجموعة لا للميسّر (BR-209).
7. **عهدة جزئية:** رصيد 2000 لعهدة 3240 ← تحويل 2000 + دفعة مؤجلة 1240 (BR-516).
8. **بند صرف مرفوض:** يفك الحجز؛ المستلم يرفع نموذجاً جديداً (BR-519/520).
9. **تكرار صورة فاتورة:** تنبيه للمراجع، والقرار له (BR-521).
10. **إغلاق بعجز:** تسوية خارجية بمستند؛ بلا مستند ← رفض (BR-523).
11. **قفل التقييم:** ق.ع يحفظ فيُقفل؛ تعديل ثانٍ ← 423؛ م.ت يفتح بسبب فيصل إشعار (BR-603).
12. **حضور بالمتأخر:** رحلتان مبكر وواحدة متأخر ← 0.8333 (08 §8.7).
13. **قبل نشر التشكيل:** مشارك يرى «تواصل مع الإدارة» ولا مجموعة ولا ترتيب (BR-017/614).
14. **تسرّب الوجود:** طلب `GET /committees/ID_غير_موجود` و`/ID_ممنوع` متطابقان (BR-014).
15. **رابط الداعم:** 5 كلمات خاطئة ← قفل 15 دقيقة؛ جهة معطّلة لا تدخل؛ تعليق pending لا يظهر (BR-803/807).
16. **تعارض صفات:** تعيين ميسّر مسؤولاً للمالية ← رفض برسالة القاعدة (BR-009).
17. **تعديل بند بدأ:** رفض (BR-214)؛ بند لم يبدأ ← يُقبل بلا اعتماد.
18. **التوزيع المشترك:** مجموع الحصص ≠ الفاتورة ← رفض (BR-525).
19. **سباق:** ضغطتا «حوّل» ← حركة واحدة (BR-536).
20. **إدخال شخص:** حساب بلا كلمة ← م.ت يولّد مؤقتة ← تغيير إجباري (BR-004/006).

## 19. المخاطر والقرارات الصعبة

| الخطر | الأثر | التخفيف |
|---|---|---|
| **اتساع النطاق**: الديمو واسع (60+ شاشة) وقابل للتفرع | تأخر وتكلفة | الالتزام بالمراحل؛ كل شاشة تُقبل بمقارنتها بالجدول (أ)؛ تجميد ما بعد المرحلة 8 للتحسينات |
| **صحة المال**: سباقات، تقريب، تعديل بعد الإغلاق | أخطاء مالية يصعب إصلاحها | `numeric`، معاملات + أقفال، triggers، append-only، idempotency، `reconcile` ليلي، property tests (07 §7.13) |
| **مطابقة النقاط مع الديمو** | ثقة المشاركين بالترتيب | اختبار parity في CI؛ دالة واحدة؛ وثيقة 08 كمرجع؛ قرار س-04 وس-05 قبل الإطلاق |
| **منطق الديمو بلا فحوص صلاحية** (س-25) | تسرب أو تجاوز | يُبنى `can()` أولاً وكل نقطة API تمر به؛ اختبارات رفض لكل انتقال |
| **قيود الاستضافة/الخصوصية** (س-01) | منع الإطلاق أو إعادة بناء | قرار مبكر؛ تجريد التخزين/القاعدة؛ تشفير الحقول الحساسة |
| **نقطة فشل واحدة: م.ت لكلمات المرور** بلا إيميل | تعطّل الدخول | وجود نائب لـم.ت (تعارض الصفات يسمح بصفة واحدة؟ — قرار)، توثيق، تفعيل البريد مبكراً (س-07) |
| **الاعتماد على الزمن** (مواعيد، فتح الخطة، بدء الجدول) | سلوك خاطئ أو مفقود | مجدول idempotent + ساعة قابلة للحقن في الاختبار + منطقة زمنية موحّدة (س-09) |
| **تعقيد RLS** | بطء تطوير وأخطاء | RLS على الحساس فقط (القسم 12.4)، اختبارات SQL، والتطبيق هو الحاكم الأساسي |
| **تفرد الجهة بكلمة المرور** (الداعم) | هوية ضعيفة | س-12: كلمات مولَّدة طويلة وقفل لكل IP |
| **أسماء حقيقية في بيانات الديمو المنشورة** (س-16) | خصوصية | seed مُخفى الهوية؛ مراجعة نشر الديمو |
| **اختلاف الوثائق** | بناء على قرار قديم | جدول 0.3 وترتيب الأسبقية؛ المراجعة مع المالك قبل كل مرحلة |
| **ازدياد حجم الملفات والتخزين** | تكلفة | حدود وضغط في المتصفح، الفيديو روابط خارجية |
| **اعتماد على مطوّر/مساعد واحد** | استمرارية | هذه الوثائق + اختبارات BR + CI صارم |
| **تحوّل المتطلبات أثناء البناء** (القرارات تتغير أسبوعياً في الديمو) | إعادة عمل | الإعدادات كبيانات، آلات الحالة في `packages/domain`، migrations صغيرة، تحديث الوثائق مع كل قرار |
